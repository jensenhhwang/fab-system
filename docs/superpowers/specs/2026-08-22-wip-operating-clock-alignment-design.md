# WIP 공통 운영시계 정합화 설계

## 배경

Twin에는 실제 경과시간에 24를 곱하는 공통 운영시계가 이미 있다. 발주 ETA, 입고, 최종 테스트,
자동출하와 운영일 집계는 이 시계를 사용하지만 WIP 진행은 아직 별도 규칙으로 움직인다.

- M20/HBM `PER_LOT`은 `lastEventAt`에서 벽시계 5초가 지났는지로 진행 대상을 고른다.
- M21/DRAM·M22/NAND `STEP_BUCKET`은 tick이 실행될 때마다 모든 버킷을 한 스텝 이동한다.
- 따라서 tick 주기나 서버 부하가 생산속도를 바꾸며, 제품별 route 스텝 수에 따라 서로 다른 배속이
  만들어진다.

이는 `RULES.md`의 “모든 생산·시뮬레이션 기능은 공통 Twin 운영시계를 사용하며 실제 1시간은
운영시간 1일이다”라는 계약과 맞지 않는다.

## 목표

1. M20·M21·M22 WIP 진행량을 `elapsedOperatingDays` 하나로 계산한다.
2. tick 횟수와 tick 간격을 바꿔도 같은 운영시간 동안의 생산량이 같아야 한다.
3. `lastEventAt`, `createdAt`, `updatedAt`은 감사용 벽시계로만 남기고 진행 판정에 사용하지 않는다.
4. 기존 자재 결품 게이트와 완제품 창고 게이트를 보존한다.
5. 대량 동시 이동으로 생기던 자재 소모·EMA·발주 폭주를 완화한다.
6. 기존 WIP를 삭제하거나 재부트스트랩하지 않고 점진적으로 전환한다.

## 비목표

- 공정별 실측 체류시간 마스터를 새로 추정하지 않는다.
- 설비별 처리능력, 다운타임, 재작업 확률을 이번 변경에 추가하지 않는다.
- WATCHED 로트의 사용자 수동 공정 완료 이벤트 의미를 바꾸지 않는다.
- 24× 배속이나 제품별 cycle time 기준값을 변경하지 않는다.

## 검토한 대안

### A. 운영시간 비례 진행 — 채택

공통 운영시계의 경과분을 각 제품의 route 체류시간으로 환산한다. M20은 개별 로트의 다음 예정
운영시각을 사용하고, M21·M22는 집계 버킷 일부를 연속적으로 이동한다.

장점은 tick 분할 불변성, 소모 평탄화, 기존 데이터 무손실 전환이다. 두 WIP 표현 방식에 맞는
구현이 각각 필요하지만 장기 운영 안정성이 가장 높다.

### B. 평균 스텝 체류시간마다 전체 한 단계 이동

`cycleTimeDays / totalSteps`가 지날 때마다 전체 WIP를 한 칸 이동한다. 구현은 단순하지만 약
35~45분마다 생산·자재 소모가 한꺼번에 발생한다. 기존의 동기화 폭주를 다른 간격으로 옮길 뿐이라
채택하지 않는다.

### C. 공정별 체류시간 마스터 신설

가장 현실적이지만 검증된 공정별 체류시간 데이터가 없다. 이번에는 균등 체류시간을 명시적 가정으로
사용하고, 향후 실측 마스터가 승인되면 같은 운영시각 인터페이스에 연결한다.

## 공통 시간 계약

엔진은 제품 루프 밖에서 한 번 계산한 아래 값을 모든 제품에 전달한다.

- `operatingEpochMs`: 이번 tick 종료 시점의 운영 절대시각
- `elapsedOperatingDays`: 직전 tick 이후 실제 경과시간 × 24
- `recordedAt`: 실행 사실을 기록하는 벽시계 시각

평균 스텝 체류시간은 다음과 같다.

```text
stepDwellDays = cycleTimeDays / totalRouteSteps
```

이는 제품별 임의 배속이 아니라 승인된 cycle time을 route에 배분하는 물리 모델이다. 모든 제품의
운영시각 자체는 동일한 24× 시계로 흐른다.

## M20/HBM 개별 로트 진행

### 운영시각 필드

`WaferLotDoc`의 엔진 관리 로트에 `nextStepOperatingMs`를 추가한다. 진행 대상은 다음 조건으로만
선정한다.

```text
status = IN_PROGRESS
cohort in [AGGREGATE, MODELED_FOUP]
nextStepOperatingMs <= operatingEpochMs
```

`lastEventAt`은 조회 조건에서 제거한다. 실제 진행이 일어난 시각을 기록하는 감사 필드로만 갱신한다.

### 기존 로트 전환

`nextStepOperatingMs`가 없는 기존 로트는 삭제하거나 한꺼번에 진행시키지 않는다. 현재
`operatingEpochMs`부터 한 스텝 체류시간 사이에 결정론적으로 분산한 예정시각을 부여한다. 분산값은
로트 ID의 안정적인 해시로 계산해 재시작해도 결과가 달라지지 않게 한다.

첫 전환 tick은 예정시각 초기화만 수행한다. 이로써 기존 1만 4천여 로트가 동시에 이동하는
마이그레이션 폭주를 막는다.

### 신규 투입과 공정 완료

- 신규 투입 로트: `nextStepOperatingMs = operatingEpochMs + stepDwellMs`
- 정상 진행 로트: `nextStepOperatingMs += stepDwellMs`로 예정시각을 이어간다. 한 tick의 운영시간 창에
  예정 이벤트가 둘 이상 들어오면 그 수만큼 순서대로 처리한다.
- 완료 로트: 기존과 같이 `DONE`, 완료 웨이퍼 수량, 완제품 테스트 대기열 입력을 생성한다.

이전 예정시각에서 이어가야 같은 운영시간을 한 번에 처리하거나 여러 tick으로 나눠 처리한 결과가
같다. 공통 운영시계가 한 tick에 반영하는 catch-up을 최대 운영 1일로 제한하므로, 한 로트가 한꺼번에
지나갈 수 있는 스텝 수도 자연스럽게 제한된다. 구현에서는 추가로
`ceil(elapsedOperatingDays / stepDwellDays) + 1`을 로트별 안전 상한으로 둔다.

### 게이팅

자재가 `COVERAGE_CRITICAL`이거나 최종 스텝의 완제품 창고가 `CAPACITY_OVER`이면 로트는 이동하지
않는다. 최초 차단시각은 기존 필드에 기록하고 `nextStepOperatingMs`를
`operatingEpochMs + stepDwellMs`로 옮긴다. 결품·창고 정체 시간은 실제 cycle time 지연으로 남으며,
해제 직후 밀린 여러 스텝을 몰아서 통과하지 않는다.

조회 배치 상한은 현재 제품 설정을 유지한다. 상한이 목표 WIP보다 크므로 차단 로트가 FIFO 선두를
점유해 다른 스텝을 굶기는 현상을 방지할 수 있다.

## M21·M22 집계 버킷 진행

`STEP_BUCKET`의 `counts[i]`는 개별 실물 ID가 없는 FOUP-equivalent이므로 소수 수량을 허용한다.
집계 계산은 공통 **운영 5분 퀀텀**으로만 실행한다. 엔진 상태의 `wipFlowCarryMs`에 경과 운영시간을
누적하고 완성된 퀀텀 수만 처리한 뒤 5분 미만 잔여시간을 다음 tick으로 이월한다. 이 값은 제품별
시계가 아니라 동일한 공통 운영시계의 수치적분 잔여분이다.

각 퀀텀에서 스텝별 이동량을 다음처럼 계산한다.

```text
moveFraction = min(1, quantumOperatingDays / stepDwellDays)
moved[i] = counts[i] * moveFraction
```

모든 스텝 이동은 같은 이전 스냅샷을 기준으로 계산해 한 하위 구간 안에서 여러 스텝을 순간 통과하지
않게 한다. 이동분은 다음 버킷으로 가고 마지막 버킷 이동분은 완료량이 된다. 신규 투입량도 같은
운영시간 구간에 비례해 step 0에 더한다.

운영 5분은 세 제품의 평균 스텝 체류시간보다 충분히 작다. 실제 시간으로는 12.5초이며, 정상 5초
tick 두세 번의 경과분이 모일 때마다 부드럽게 진행된다. 운영 1일 catch-up도 288개 퀀텀으로 나뉘어
한 번의 전체 시프트나 완제품 폭증이 생기지 않는다. 같은 총 운영시간을 한 번에 주거나 여러 tick으로
나눠도 처리한 퀀텀 수와 잔여시간이 같으므로 결과가 같다.

자재 또는 완제품 게이트가 막힌 스텝의 이동량은 0이며 해당 수량은 제자리에 남는다. 다른 스텝은
동일한 운영시간만큼 계속 움직인다. 차단 해제 후에는 정상 속도로 재개하고 밀린 물량을 한 tick에
몰아서 통과시키지 않는다.

## 자재 소모와 완제품

자재 소모량은 실제로 스텝을 떠난 웨이퍼 수량만으로 계산한다.

- M20: 실제 이동한 개별 로트의 `waferQty`
- M21·M22: 이동한 FOUP-equivalent × `wafersPerFoup`

EMA 정규화 분모는 기존처럼 같은 `elapsedOperatingDays`를 사용한다. 이동량과 분모가 동일한 시간축을
사용하므로 벽시계 5초 기반 폭증이나 tick당 전체 시프트 기반 폭증이 사라진다.

완료량은 기존 최종 테스트 대기열과 자동출하 흐름을 그대로 통과한다. 이번 변경은 그 앞단의 WIP
도착 속도만 바로잡는다.

## 레거시 자동 진행 제거

`listActiveLotStates`가 조회 과정에서 벽시계 5초를 보고 WATCHED 로트를 자동 진행시키는 동작은
운영시간 규칙과 조회 무변경 원칙을 모두 위반한다. 목록 함수는 생성·조회만 수행하도록 바꾸고,
WATCHED 로트 진행은 기존 명시적 `advanceLotStep` 호출만 허용한다.

`AUTO_ADVANCE_INTERVAL_MS`, desync 지터, 벽시계 due 테스트는 엔진 진행 경로에서 제거한다. 감사
타임스탬프 필드는 유지한다.

## 데이터 호환성과 복구

- 기존 M20 WIP: lazy backfill로 `nextStepOperatingMs`를 추가한다.
- 기존 M21·M22 버킷: 정수 배열을 그대로 읽고 이후부터 소수 FOUP-equivalent로 저장한다.
- `releaseCarryByProduct`: M20 정수 로트 투입의 소수 이월에 계속 사용한다. 집계 버킷 제품은 연속량을
  직접 반영하므로 새 정수 carry를 만들지 않는다.
- `wipFlowCarryMs`: 공통 운영 5분 퀀텀에 못 미친 잔여 운영시간만 저장한다. 최초 전환 시 0으로
  시작하므로 배포 전 시간을 소급 진행하지 않는다.
- 롤백 시 추가 필드는 구버전 코드가 무시하므로 스키마 파괴가 없다. 버킷의 소수값도 `number[]`
  타입과 MongoDB Number 표현 범위 안에 있다.

별도의 파괴적 데이터 마이그레이션이나 WIP 초기화는 하지 않는다.

## 오류 및 경계 처리

- `elapsedOperatingDays <= 0`: WIP 이동과 자동 투입을 하지 않는다.
- route가 없거나 스텝 수가 0: 기존처럼 빈 결과를 반환한다.
- 잘못된 cycle time: 진행하지 않고 명시적 오류를 남긴다.
- 부동소수점 잔량: 매우 작은 음수·잔량은 epsilon 기준으로 0에 고정한다.
- catch-up: 공통 시계의 운영 1일 상한을 유지하고 집계 버킷 내부에서 하위 구간 처리한다.
- 동시 tick: 기존 전역 Twin lock을 유지한다.

## 검증 기준

### 순수 계산 테스트

1. 같은 운영시간을 한 번에 주거나 여러 tick으로 나눠도 최종 WIP·완료·소모가 개별 로트 정수화
   허용 오차 안에서 같다.
2. 경과 운영시간이 0이면 어떤 WIP도 움직이지 않는다.
3. 실제 1시간은 운영 1일의 진행량을 만든다.
4. 제품별 장기 완료량이 `dailyLotRelease`에 수렴한다.
5. 자재·완제품 게이트가 걸린 스텝은 이동하지 않고 해제 후 폭주 없이 재개한다.
6. M21·M22 버킷의 총량은 `이전 WIP + 투입 - 완료`와 일치한다.

### 통합 회귀 테스트

1. M20 due 판정이 `lastEventAt`을 읽지 않는다.
2. 기존 M20 로트의 예정 운영시각이 결정론적으로 분산 초기화된다.
3. 신규 M20 로트가 평균 스텝 체류시간 전에 이동하지 않는다.
4. M21·M22가 tick 한 번만 왔다는 이유로 전체 한 스텝 이동하지 않는다.
5. 완료 웨이퍼, 자재 burn, 최종 테스트 대기열, 자동출하 연결이 유지된다.
6. 기존 24× 운영시계, 재투입, 자재 서킷브레이커, 완제품 용량 게이트 테스트를 새 계약에 맞춰 갱신한다.
